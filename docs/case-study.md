# 案例：跨境小电商的运营周报

这份文档是 InsightFlow 的**业务场景说明**，回答三个问题：谁在用、原来怎么做、换成这套之后变成什么样。

> **数据来源**：公开数据集 UCI Online Retail II（2010-12 至 2011-12 的英国在线零售商交易记录），
> 本文只使用其中德国站与法国站 2011 年全年共 **17,049 行**明细。
> 角色与流程是**按真实运营工作复刻**的，不是某家公司的内部项目；所有数字均可用仓库内脚本复算。

## 场景

| | |
|---|---|
| 角色 | 一名运营，同时管德国站和法国站 |
| 数据 | 交易明细 17,049 行（1,990 个 SKU、177 个客户），含退货、缺失客户号、零价行 |
| 节奏 | 每周一早上出一份周报，同时随时被问"上周为什么跌" |
| 工具 | Excel + 手工透视表 |

## 原来的流程与痛点

1. 从后台导出订单明细（CSV）
2. Excel 透视：按国家、按月算销售额；按发票数算客单价
3. 手工挑前几名 SKU，看退货金额
4. 写结论：三五百字 + 一两张图
5. 被追问细节时回到第 1 步重新捞数据

**耗时**：每周约 90 分钟，其中一半花在重复的透视上。

**真正的痛点不是慢**，而是三件事：

- 只来得及看总量，看不出"哪个国家在掉"；
- 结论没有出处，被问"这个数字哪来的"要重新算；
- **遇到脏数据没有防线**——比如把运费、手工调整当成商品算进退货率。

## 换成 InsightFlow 之后

上传两个 CSV（订单明细 + 商品维表）→ 提问题 → 得到带图的报告，每个结论都附来源与计算口径。

**耗时**：首次配置约 3 分钟，之后每次分析 2–5 分钟。

## 五个每周都要回答的问题

以下是 2011 年真实数据的**标准答案**（脚本复算，`scripts/prepare_retail_case.py` 生成数据后可复现）：

| # | 问题 | 标准答案 |
|---|---|---|
| 1 | 最近两个完整月，GMV 环比如何？ | 10 月 52,431.25 → 11 月 53,469.46，**+2.0%** |
| 2 | 退货金额最高的商品是哪些？ | `22423 REGENCY CAKESTAND 3 TIER` 退货 809.70（占该 SKU 销售额 7.5%）；其后为 `22236`、`22634`、`21843` |
| 3 | 整体退货率（按金额）？ | 退货 6,479.59 / 销售 368,343.18 = **1.76%** |
| 4 | 新客与老客的客单价差异？ | 新客 598.70，老客 490.74（老客单价更低，但笔数是新客的 2.9 倍） |
| 5 | 哪个国家季度收入在涨但客单价在跌？ | 德国：Q4 收入 67,647.61（Q3 53,752.97，**+25.8%**），客单价 473.06（Q3 475.69，**−0.6%**） |

## 两个真实陷阱（也是这套系统的价值所在）

**陷阱一：12 月只有 9 天。** 数据截止 2011-12-09。直接算"11 月 → 12 月"会得到 **−74.4%** 的暴跌结论，而真相是当月数据没跑完。任何以 12 月为终点的环比都不成立。

**陷阱二：`M` 和 `POST` 不是商品。** 它们是手工调整与运费。不排除的话，退货率榜单第一名会是 `M`（退货 11,730.30，占其销售额 99.5%），看起来像"某商品几乎全退"，实际是会计科目。排除这些非商品行（共 678 行）后，真实整体退货率是 1.76%。

一份合格的分析报告，必须**主动说出这两件事**：数据截止到哪、哪些行被排除。说不出来，数字越精确越危险。

## 真实模型跑出来的结果

同一批数据、同一个问题，用真实模型（经 ModelGate → DeepSeek）跑过两次：

**第一次，没有把口径交给模型：**

| 项 | 模型给出的答案 | 标准答案 |
|---|---|---|
| 月份 | "两个完整自然月 11 月与 12 月" | 12 月只有 9 天，不可比 |
| GMV 环比 | **−74.44%** | 10→11 月 **+2.0%** |
| 退货冠军 | **`M`（手工调整，11,730.30）** | `22423`（809.70） |

报告结构、图表、结论表述都正常——错在业务常识。

**第二次，把 `knowledge/retail_data_notes.md` 作为知识源一并传入：**

| 项 | 模型给出的答案 | 标准答案 |
|---|---|---|
| 月份 | "10 月与 11 月为唯一可比的完整月份"，并指出 12 月截止 12-09 | 一致 |
| GMV 环比 | **+1.98%**（52,431.25 → 53,469.46） | +2.0% |
| 退货冠军 | **`22423`（809.70）** | 一致 |
| 非商品编码 | 明确"已排除 M/POST 等非商品编码" | 一致 |

两次运行都是 `completed`、3 张图表、约 26 次模型请求、95 秒左右。

这说明本项目的价值不在"模型很聪明"，而在**口径可以被写成文档、被检索、被复用**，
而模型的输出可以被同一份口径约束。
## 验收标准

| 项 | 要求 |
|---|---|
| 结论可追溯 | 每个数字能追到具体表格与计算口径 |
| 口径显式 | 退货是否计入 GMV、非商品行是否排除，必须写明 |
| 数据缺陷报警 | 期间不完整、字段缺失、异常值时明确提示，而不是照算 |
| 拒绝回答 | 数据里没有的维度（例如"广告投放效果"）要直接说不支持 |

最后一条最重要：**一个会说"这个我算不了"的系统，比一个什么都敢给数字的系统可信。**

## 复现

```bash
# 1. 下载公开数据（约 45 MB，不进仓库）
#    https://archive.ics.uci.edu/static/public/502/online+retail+ii.zip

# 2. 生成案例数据（德国 + 法国 2011）
python scripts/prepare_retail_case.py --source path/to/online_retail_II.xlsx

# 3. 起服务并分析
python scripts/serve_api.py --port 8123
```

## 局限（面试时要主动说）

- 数据是公开数据集，**不是客户数据**；角色与流程是复刻的，不是某公司真实项目
- 交易记录是 2011 年的，不含广告、库存、物流成本，所以只能回答"卖得怎么样"，不能回答"为什么"
- 真实模型的结论质量依赖提示词与数据质量，本文给出的标准答案由脚本计算，不依赖模型
