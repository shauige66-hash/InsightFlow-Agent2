# InsightFlow-Agent2 · 项目说明

**定位**：面向中小电商运营与代运营团队的**周期性经营分析 Agent**。

用户上传订单、商品等结构化业务数据和业务规则文档，用自然语言提出经营分析问题。
多 Agent 工作流自主规划分析任务，路由到 Python / SQL 执行，结合 RAG 检索业务口径，
按执行反馈进行修复与调整，最终生成包含指标、图表、分析结论及知识来源的经营分析报告。

**核心价值**：减少重复的数据整理、指标计算与报告编写，让周期性经营分析的结果
可追溯——每个数字能追到具体任务、计算口径与知识来源。

**技术栈**：Python 3.11 · LangGraph · FastAPI · PostgreSQL + pgvector · Redis · Docker · pytest
**仓库**：github.com/shauige66-hash/InsightFlow-Agent2

## 一、谁在用，解决什么问题

**目标用户**：主要是中小电商的运营分析人员；潜在使用方是小型代运营团队与数据服务团队
——1–5 人小团队里兼做数据的那个人，不是专业分析师。

**核心场景**：跨境电商周期性经营复盘。模拟用户是一名负责德国站与法国站的运营，
每周固定回答五个问题：GMV 环比、退货最高的商品、整体退货率、分国家表现、数据质量。

**原来怎么做**：导出 CSV → Excel 透视 → 挑数 → 手写结论，每周约 90 分钟。
只来得及看总量；结论说不出出处；遇到脏数据（月份不完整、运费被当成商品）会得出
错误结论且不自知。

**改成什么**：上传表 → 提固定的几个问题 → 拿到带图、带口径、带来源的报告，
可选推送飞书群。

**不适用**：单次、小数据、临时问一句——那用通用对话模型更快。这套的价值在**重复**、
**口径一致**与**可追溯**。

**边界**：分析由人工触发（没有业务侧定时自动分析）；数据里没有的维度（广告、库存、
物流成本）回答不了；场景筛选与试点建议见 [business-opportunities.md](business-opportunities.md)，
均未实现。

## 二、做法

一条 24 个节点的 LangGraph 流水线：数据加载 → 上下文 → 知识检索 → 规划 → 计划校验 →
〔计划审批，可选〕→ 路由 → 执行（容器内 / 只读 SQL）→ 审查 → 决策 → 推进 →
可视化规划 → 图表生成 → 报告 → 〔发布审批，可选〕→ 产物；预算耗尽时经
`budget_stop` 安全收尾，仍产出已有结论与失败说明。

**1. 治理收敛到唯一入口。** 模型调用与工具执行都经过 `harness/`，预算、账本、幂等
只实现一次。预算按**真实上游请求**计数并前置于请求：上限 3 次就恰好 3 次。曾发现
一个真实缺陷——节点只返回部分 state 让累计用量回退，上限 3 实际发了 4 次。

**2. 计划不信任模型自评。** 程序校验任务结构、ID 唯一性、目标表是否属于本次 Run 的
授权资源、来源类型能否落到单一工具、依赖是否成环；不合法携带原因重写，最多 3 次。
审批记录计划指纹，执行前比对。

**3. 动态决策有边界，且可配置。** 开启 `enable_dynamic_loop` 后，任务执行完先构造
观察，模型在 7 个动作里选一个，再由确定性策略校验：权限/授权/环境/预算类失败
**禁止重试**；决策步数、重规划、补检索、重复动作各有硬上限。API 层默认关闭，
控制台默认勾选——它是可配置能力，不是所有运行的必经环节。

**4. 结论可追溯、可被口径约束。** 业务口径写成可检索的知识文档而非提示词；报告附
来源附录（文档、页码、chunk、相似度）与图表；被拒绝的图表与失败任务写进报告附录
而不是被隐藏；口径变化即失效旧证据。

**5. 提示词优化是受控的离线闭环（可选）。** `improvement/` + `eval/` 提供
"真实重复评测 → 候选搜索（内置 reflective 或官方 GEPA SDK）→ 独立验收 → 版本晋升
与回退"的命令行闭环：候选只是 Planner/Critic 的附加指引与结构化经验（纯文本），
评分由宿主侧独立 oracle 完成，晋升条件是候选改不了的固定规则；不训练模型参数、
不改应用源码。详见 [improvement.md](improvement.md)。

## 三、证据

**工程**

| 指标 | 数值 |
|---|---|
| 自动化用例 | 全量 `pytest`（2026-11-16，本机含 Docker，基线 `6b2f2f8`）：**1384 通过 / 67 跳过 / 0 失败**，约 21 分钟；测试策略见 [testing.md](testing.md) |
| 执行侧上下文 | 5 表场景单任务 4236 → 847 字符（**−80%**） |
| 预算准确性 | 上限 N 次 → 恰好 N 次真实请求（用例断言） |
| 崩溃恢复 | 3 个窗口跨进程强杀 + PostgreSQL 重连 |
| 数据隔离 | 令牌 → 归属者，越权读他人会话返回 404 |

> 测试环境说明：全量回归依赖本机 Docker（Python/绘图在容器沙箱执行）；Docker 未启动时
> 沙箱相关用例会成批失败（旧基线实测 24 个失败全部源于 `docker daemon is not
> available`，启动后恢复）。67 个跳过里包含可选的 GEPA SDK 用例——本机未安装
> `gepa`（`requirements-improvement.txt`），属可选依赖，适配器逻辑由不依赖 SDK 的
> 用例覆盖。上一基线（`45ca142`）曾有的 1 个已知失败（恢复用例断言脚本化模式下
> 产出 PDF）已在 `6b2f2f8` 修复：用例改为断言按设计降级（无 PDF、状态 degraded、
> 原因与日志一致），并加强"reporter 只被调用一次"等断言。

**真实模型**（经 ModelGate → DeepSeek 的**历史运行**，不构成对后续运行的保证）

| 场景 | 结果 |
|---|---|
| 小数据（8 行订单 / 5 客户） | completed，3/3 图表，18 次请求，约 100 秒 |
| 零售案例（17,049 行 / 1,990 SKU / 177 客户） | completed，3/3 图表，26 次请求，约 95 秒 |

当前代码对图表逐张校验（来源任务成功、图表类型合法、目标表匹配），不合法的图表会被
拒绝并写入报告附录——因此后续运行的图表数可能少于计划数，这是设计行为。

**对照实验：口径的价值**（同一份数据、同一个问题，两次真实运行）

| | 无口径 | 有口径 | 标准答案（脚本复算） |
|---|---|---|---|
| 月份判断 | "11、12 月两个完整月" | "10、11 月是唯一可比月份，12 月截止 12-09" | 12 月只有 9 天 |
| GMV 环比 | **−74.44%** | **+1.98%** | +2.0% |
| 退货冠军 | **`M`（手工调整）** | `22423` | `22423`（809.70） |

两次工程链路都正常（3 张图、completed、报告结构完整），**错的是业务常识**。把口径写成
知识文档随分析传入，同一个模型给出正确答案。这是"系统"相对"直接问模型"的差别：口径
可被检索、审阅、按租户替换。标准答案是这份数据的历史复算结果，不是准确率承诺。

## 四、局限

1. 评测用脚本化模型验证工程链路，真实模型的结论只在小样本上验证过。
2. 认证是"令牌 → 归属者"的简单映射，没有注册、配额、账单。
3. 沙箱依赖宿主 Docker；Docker Desktop 上建议本机直接跑。
4. 队列只支持 PostgreSQL，`claimed` 超时回收需人工 `requeue`，无自动重试。
5. 单机部署，未验证水平扩展；PDF 导出依赖浏览器环境，缺失时降级为 Markdown + HTML。
6. 自我改进闭环当前的评测任务是**一个业务问题的六组同领域合成数据变体**，用于跑通
   闭环；真实模型上的候选收益与跨领域泛化仍需显式授权的评测确认。

## 五、怎么验证

演示手册（真实数据、逐步操作）：[demo/README.md](demo/README.md)

```bash
python scripts/check_model.py                            # 凭据是否可用（401/402/404）
python scripts/real_model_smoke.py                       # 真实模型跑一次完整分析
python scripts/real_model_regression.py --include-retail # 固定用例回归，带历史对比
python -m pytest -q                                      # 全量自动化回归（脚本化模型，不访问付费 API）
python scripts/run_improvement.py status                 # 自我改进闭环入口（需评测专用凭据，见 improvement.md）
```
