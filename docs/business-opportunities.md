# InsightFlow 业务场景与商业价值判断

调研日期：2026-10-25。依据当前代码、项目既有案例和产品官方文档。本文是场景筛选与试点建议，不是客户需求、准确率或收入验证。

## 结论

最值得做专项验证的是：**给中小 ERP/BI 实施团队使用的离线报表口径核验与差异排查助手**。它的任务、交付物和判对标准，比通用经营建议更具体。

当前代码复用最多的是：**数据服务商的非标准经营分析交付**。金额价值更直接、但业务能力缺口也更大的是：**电商结算、费用与退款例外复核**。

目前没有证据证明本项目在这三类场景中已经显著领先成熟产品。可能形成明显优势的条件是：客户多、导出表格式不统一、口径经常变化、需要读业务说明并追问、最终由专业人员复核。这里要比较的是现有的定制人工流程，不能未经测试就宣称胜过专业对账系统或 BI。

## 1. 当前代码实际能提供什么

| 已有基础 | 目前边界 | 业务含义 |
|---|---|---|
| CSV、XLSX、SQLite 加载，多表分析 | 无现成 ERP、电商、支付平台业务 API 连接器；同任务 SQLite 与文件混用会拒绝 | 试点从客户导出文件开始，不能宣传实时全平台接入 |
| 业务文档 RAG、上下文、已确认记忆 | 文档口径多数仍经提示传给模型，并非全部由程序强制执行 | 金额、期间、排除项、容差等重要规则要固化并独立核验 |
| Python/SQL 生成执行、Repair、Refine、动态决策 | 执行成功与 Critic 通过不等于业务答案正确 | 可以辅助排查，不能由模型自行裁定最终验收 |
| Harness、审批、预算、Checkpoint、调用记录 | 属于运行治理，不是财务内控或审计认证 | 有助于受控交付，不能替代业务规则和审核责任 |
| 报告、图表、知识来源附录、输入内容指纹 | 来源主要是文档/页码/chunk；未形成每个数字到原始行、公式/SQL、规则版本的完整追溯 | 差异核查需要新增逐项证据包 |
| 飞书 Run 完成和审批提醒 | 未实现完整业务工单处理、反馈回填和定时调度 | 先人工触发与复核；队列不等于定时巡检 |
| 提示与经验优化、独立评分框架 | 当前新增任务集只有一种业务问题的六组合成变体 | 新场景必须建立自己的标准答案和验收规则 |
| 本地服务和容器执行 | 模型按配置地址接收上下文 | 本地部署不自动等于数据不出域 |

核对入口：`ingestion/loader.py`、`ingestion/resources.py`、`planning/validator.py`、`nodes.py`、`services/run_notifier.py`、`core/llm.py`、`eval/real_tasks.py`。既有零售案例使用公开历史数据复刻流程，不是客户上线证据，见 `docs/case-study.md`。

## 2. 推荐验证：ERP/BI 实施团队的离线报表差异核查

**潜在买方**：承接多个客户的 ERP/BI 实施商、数据开发外包团队、负责报表交付的项目负责人。

**具体触发**：系统迁移、报表重写、统计口径变更后，新旧报表数字不一致，需要找出差异、解释差异，并由客户确认。先限定导出文件、小规模离线批次，不承诺整个 ERP 或大规模数据库迁移测试。

**输入**：新旧两套导出表、业务主键与字段说明、双方确认的口径、已知例外。

**交付物**：字段映射建议；待确认的期间、税费、退款等口径；确定性计算产生的差异明细；可能原因及对应证据；人工确认与重跑记录。

**示例，属于产品设想**：旧报表按下单日统计，新报表按支付日统计；另有取消订单排除规则不同。系统先提出这些待确认差异，程序按已确认规则逐项复算，再列出仍未解释的订单。模型不能把所有差异解释成错误，也不能自己批准上线。

**可能较大的优势**：一个实施团队同时遇到多个客户、不同字段和不同口径时，减少反复读说明、写临时查询、组织差异解释的工作。业务规则与差异证据如果能积累为可重放测试，下次报表变更还可复用。

**商业价值**：减少排查、返工和解释工时，帮助完成交付验收。可探索按核查项目/验收包收费，再转为团队订阅和规则维护；不是给“AI 聊天”定价。

**竞争反证**：Tricentis 已提供跨系统数据集比对、报表测试和业务逻辑校验；Soda 已提供迁移前后指标与记录对账。这是已有商业供给，并非无人解决的市场。本项目的机会只能是特定团队的轻量文件工作流与定制交付效率，仍需比较验证。[Tricentis 文档](https://docs.tricentis.com/tosca-cloud/en-us/content/data_integrity/di_intro.htm)、[Soda 迁移核验文档](https://docs.soda.io/soda-documentation/soda-v3/use-case-guides/quick-start-migration)。

**必须补齐**：确定性比对器，主键/粒度/期间/单位/币种/容差规则，逐行差异与完整证据包，人工签核。不能只加一段提示词就宣称具备验收能力。

## 3. 最容易复用现有工程：数据服务团队的定制分析交付

**潜在买方**：代运营、经营咨询、外包数据分析团队负责人。先服务专业交付人员，而不是直接假定所有店老板都需要新的分析软件。

**具体触发**：不同客户定期交来订单、商品、售后等表格，口径也不同；分析师整理、复算、写报告，交付后继续回答追问。

**输入与交付**：客户导出文件和业务说明，输出经过人工核对的指标、异常明细、报告和追问答案。

**可能较大的优势**：长尾问题与客户格式不断变化时，可以用现有规划、代码执行、修复、知识检索和报告能力准备交付初稿，减少逐客户从头搭仪表盘和写分析脚本的投入。客户规则须隔离、确认、可测试；不能让一个客户经验自动污染其他客户。

**商业价值**：降低单次交付总工时，减少返工；有额外订单时才可能转化为更多交付毛利。较现实的起步方式是带人工复核的分析服务或团队内部工具，收首次口径适配费和持续交付费。

**竞争反证**：AgencyAnalytics 已有多客户组织、自动报告、白标、AI 分析、客户上下文等能力，公开核心方案是每客户每月 20 美元、按年付费。因此不能把 AI 总结、RAG 口径或自动报告当独有优势。该报价只能证明商业供给，不能证明本项目或中国客户的支付意愿。[官方定价](https://agencyanalytics.com/pricing)、[客户管理文档](https://help.agencyanalytics.com/en/articles/10344666-create-and-manage-clients)。

**必须补齐**：客户交付模板、确认后的字段映射、关键数独立核对、批次管理、客户隔离的规则与经验、复核和交付工作台。数据和问题若长期固定，优先考虑固定 SQL、脚本或已有 BI。

## 4. 金额价值更直接但距离更远：电商结算、费用与退款例外复核

**潜在买方**：电商财务服务机构、多店铺商家的财务或运营负责人。

**具体触发**：订单、支付、退款、结算或服务商账单解释不一致；已有软件未能直接解释少数例外，人员仍需合表与追查。

**输入与交付**：相关导出文件及确认的结算/费率规则，输出待复核的未匹配、跨期、手续费或退款差异清单和计算证据。统计差异不能直接等同于漏款、错扣费或欺诈。

**可能较大的优势**：只针对成熟工具覆盖之外的非标准文件、自定义条款或例外解释。Agent 帮助理解字段和条款、组织排查与说明；金额、匹配、时间窗和验收由固定规则计算。

**商业价值**：减少复核工时；如确实推动处理了有效异常，可单独记录经确认的减少损失。待核查金额、已确认差异金额与实际追回金额必须分开，不能直接相加为收益。

**竞争反证**：A2X 已提供跨渠道结算对账和会计系统集成；Loop 已自动发现退货异常、按估算金额影响排序并展示退货原因。国内九数云已提供聚水潭数据接入。因此接入、对账、退货告警均不是项目现成优势。[A2X 官方](https://www.a2xaccounting.com/)、[Loop Return Insights](https://help.loopreturns.com/en/articles/13680897)、[九数云聚水潭接入文档](https://help.fanruan.com/jiushuyun/doc-view-342.html)。

Shopify 官方还明确说明销售和支付报表因统计对象与时点产生差异。这支持“解释口径差异”这一问题的存在，但不支持把差异直接认定为财务损失。[Shopify 销售差异说明](https://help.shopify.com/en/manual/reports-and-analytics/discrepancies/sales-discrepancies)。

**必须补齐**：平台文件适配、事件关联、精确金额与币种处理、费率和结算规则、误报评测、人工案件处理和回填。当前零售案例不能证明这些能力。

## 5. 什么情况下才有资格称为显著优势

应对同一份真实任务，比较原有 Excel/SQL/BI 流程、通用表格 AI 助手与本项目，记录从拿到文件到最终交付的总时间。Microsoft Copilot in Excel 已支持自然语言驱动 Python 分析、多表范围和查看生成代码；不能把“自然语言算表画图”视为独有能力。[Microsoft 官方说明](https://support.microsoft.com/en-us/excel/get-direct-answers-to-your-data-analysis-questions)。

建议的试点门槛，以下是目标而非当前结果：

1. 多份真实历史任务与后续新任务都能完成，不能仅在专门整理的演示样本上成功。
2. 总处理工时相对客户现有流程至少减少一半；计入数据准备、口径确认、模型等待、纠错、人工复核和交付。
3. 约定的关键指标和差异明细通过独立规则核验，错误与漏报不能因提速而增加。
4. 未参与调试的专业人员能按证据复查，且用户连续复用并愿意为明确交付物承担费用。

若只比人工手写报告快，却不比客户实际使用的现成工具好，不足以构成购买理由。这些小规模结果即便达标，也不能直接外推所有客户与业务。

## 6. 收益如何计算

可验证的月度价值可以拆成：实际减少的处理与返工工时乘以真实人力成本，加实际新增交付的贡献毛利及经确认的减少损失，再减接入、模型、部署、维护、复核和纠错成本。同一项收益不要重复计入。

节省工时不自动等于现金支出下降，更多交付能力也不自动等于有更多订单。定价还需结合客户替代方案、预算和试点承诺，不能从竞品报价或任意假设直接推导。

## 7. 现有技术在上述场景中的位置

| 组件 | 合理用途 | 不应承担的职责 |
|---|---|---|
| Planner / RAG | 拆解核查、检索口径、提出需确认的映射 | 自行决定正确业务口径 |
| Python/SQL / Repair | 执行计算、修复代码和格式错误 | 以执行成功证明业务正确 |
| Critic / Refine | 提醒缺项、发现待核查点、改进解释 | 自行降低验收标准或改动已核准数字 |
| 独立规则/评分器 | 核验关键数、差异明细与约定验收条件 | 把固定小任务结果泛化为行业准确率 |
| Harness / 审批 | 约束执行、额度、权限和交付确认 | 宣称审计认证或自动保证合规 |
| GEPA / 经验 | 有真实失败样本后减少已知重复错误 | 在没有用户和任务集时充当商业壁垒 |

建议下一个里程碑：通过一家实施或数据服务团队，拿到一项真实、允许使用的离线核查任务，取得原交付物与判对标准；先完成一次有人工复核的交付，再决定产品化。商业定位和功能范围仍待该试点验证，本文没有修改应用行为。
